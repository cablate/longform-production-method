# 從素材到電子報的生產方法

每期都必須做的是關鍵判斷與責任確認，不是套用相同外觀。必要資訊先取自使用者與現行專案；不足時再依 [電子報的作用與基本資料](role-and-profile.md)補齊；需要決定文章類型或深度時，再讀 [研究依據與內容類型](content-model.md)。


<a id="production-state"></a>

## 接手時先讀目前工作狀態

每篇稿件是正文與目前狀態的唯一 owner。先讀稿件、`status`、`next_action`、來源與仍有效的 JEV Gate Receipt；不靠對話記憶猜進度。舊狀態與未綁定目前版本的 Receipt 只作歷史證據，不能控制下一步。

新寫整篇才讀完整寫作與閱讀方法；接作者修改或只改主旨，不重跑選題、訪談、圖片或所有 Gate。週報與深文各自定位；共用來源只在事實更正真的影響另一篇時回查。

<a id="artifact-contracts"></a>

### 階段產物先成立，流程才可前進

不替一期電子報建立 proposal、design、spec、tasks 四份平行文件。稿件仍是唯一正文 owner；AI 在產製中維持三個可追溯產物：

| 階段產物 | 最晚何時必須成立 | 機器檢查 | 語義責任 |
|---|---|---|---|
| 可回查素材包 | 進入 `brief` 前 | `production.evidence` 至少有一個有效定位 | 來源節點確認原文、上下文、去重、支持範圍與公開限制 |
| 本期任務契約 | 進入 `draft` 前 | 有非空的「本期寫作依據」或「內部寫作依據」區 | brief 節點確認讀者處境、讀完增加的理解、主張、來源邊界、不負責事項與真正未決問題 |
| 可交付正文邊界 | 進入 `review` 前 | 正文只各有一個 `newsletter-body:start`／`newsletter-body:end`，中間非空 | 寫作節點確認主旨、預覽與正文完成同一讀者任務，內部依據不混入寄出版 |

以上檢查是前置條件，不是品質分數。缺少必要產物時，AI 先補齊或停在正確缺口；補齊格式也不代表內容正確，仍要逐一通過 JEV Gate。這讓「檔案存在」「內容品質通過」「作者接受」「已寄送」保持不同事實。

本期任務契約不要求固定文案或逐欄表單，但第一次接手的人必須能從該區回答：這篇服務誰、要完成什麼理解、哪些主張由哪些來源支持、刻意不處理什麼，以及哪些缺口真的需要作者。無法回答時留在 `brief`，不能讓模型靠擴寫正文掩蓋規格缺口。

需求或作者意圖在製作中改變時，依受影響範圍回到 `brief` 或 `sources`，再產生新的內容指紋；已通過的 Gate 收據因此失效。這相當於把規格變更先寫回上游再繼續製作，不能默默修改正文後沿用舊任務與舊核准。

等待外部輸入時，在 `next_action` 與稿內內部區寫清楚是缺來源、作者、公開許可或工具；非必要問題不升成作者待答。AI 可以自行連續完成來源整理、brief、寫作與回修，但不得自行宣告 Gate 通過。

品質 Gate 統一使用 [newsletter_gate_jev.py](../scripts/newsletter_gate_jev.py)。`experience` 與 `prose` 可直接讀稿；`brief`、`truth`、`depth`、`fidelity` 與 `final` 應使用包含任務、完整來源或交付資訊的 JSON input：

```text
python <skill>/scripts/newsletter_gate_jev.py experience drafts/<稿件>.md --output <receipt>.json
python <skill>/scripts/newsletter_gate_jev.py truth <gate-input>.json --output <receipt>.json
```

Receipt 以 input 與 artifact 雜湊綁定確切版本。稿件或依據改變後重跑受影響 Gate，不改雜湊冒充沿用；遠端來源沒有重新取得時仍標為未知。作者接受與實際寄送另需各自證據，JEV `final=pass` 也不取代它們。

<a id="quality-loop"></a>

### Gate 與回修迴圈怎麼運作

本期寫作依據完成後，先通過「本期判斷主線 Gate」，才投入全文寫作。它只檢查這篇是否已經有可由來源支持的任務、問題、證據關係與適用邊界；判斷型或案例型深文才使用四點推進，編選、通知與短札記依自身任務判定。完整成稿再依序通過來源與主張、完整與深度、閱讀體驗、作者與公開四道內容 Gate，接著通過文字與聲音後製 Gate，最後再跑交作者前的確切版本 Gate。作者接受是後續獨立事實。拆開是為了先阻止錯題進入昂貴的全文寫作，也讓每輪只判一類問題：來源錯誤不能被好讀抵銷，內容空洞也不能用語氣自然掩蓋。局部任務從第一個受影響的 Gate 開始，再跑其後會被改動影響的 Gate；不動正文的純機械檢查不必重跑全部流程。

每個 Gate 都採同一個判定契約：

1. AI 準備確切稿件、該 Gate 所需完整來源、任務與前輪 Receipt，不用自己的自評代替輸入。
2. JEV 回傳有限 outcome 與全部原子答案；一致性護欄處理「總結 pass、必要條件卻未達該面向具名門檻」的矛盾，Receipt 的正式 `outcome` 才是路由依據。一般面向的門檻是 0.5；少數研究確認的承重面向依 Gate 契約使用 0.65，不採平均分。
3. 不通過時，AI 依低信號面向回到原句與來源，形成最小修訂範圍；JEV 不生成文章或 blocker 文案。
4. AI 只修目前 Gate 指向的問題與必要相鄰承接，保護其他有效內容；修改後以新版本重跑同一 Gate。
5. 正文新增或改動事實後，從 `truth` 重跑；結構性重建後依序重跑 `truth`、`depth`、`experience`、`fidelity` 與 `prose`。
6. 同一 Gate 連續兩輪結果相同且沒有可指認改善時停止，保留未通過狀態交作者或責任編輯；不呼叫 stronger reviewer，也不因次數用完強制 PASS。

各 Gate 的問題、合法結果、輸入與 Receipt 見 [JEV 品質 Gate](jev-gates.md)。正式依據是另存且綁定目前內容的 JEV Receipt；未綁定目前 identity 的舊紀錄只作歷史參考。

## 1. 界定工作

- **從一段期間找題目：**使用者指定期間；未指定時可建議查看最近一個出刊週期，但不要假設所有人都每週出刊。
- **指定素材：**只處理指定內容，必要時補查直接來源。
- **審稿：**先確認這封信要幫讀者完成什麼，再檢查來源、結構、有沒有改壞作者原意，以及哪些內容可以公開。
- **歷史回訪：**確認舊內容今天仍成立，以及這次新增什麼。

先依 [Skill 入口](../SKILL.md)辨認編選、深入文章或其他內容任務。編選另讀 [既有內容編選](compilation-method.md)；不先套用找單一題目、發展論點與補深流程。只規劃方法時，到決策與交接安排為止，不形成電子報成品。

紀錄放哪裡、來源怎麼取得或工具是否可用，先由 AI 查現行入口與負責文件，不能當作作者訪談題。暫時找不到回饋 owner 且不影響本期判斷時，在現有稿件內部區留下必要來源定位與待定位註記，繼續可完成的工作；不複製整封私人回信，也不另造一個永久回饋庫。只有真正影響資料權限、內容取捨或需要作者知道的事實時才問。

不要把「先整理所有歷史資料」設為開始條件。已有明確任務與充分素材時，AI 自行完成可重建的選擇；只有不同方向會造成實質返工，或需作者的新立場時，才提早確認，不逐關要求核准。

選題已指向某篇長文時，先由 `brief` 形成可比較的本期任務，再對照可取得的近期候選、既有電子報與相關公開內容。分開判斷讀者問題、核心主張、承重素材與新增讀者價值，再回答「同一問題是否已有同一答案」及「本篇新增什麼」。共用題材或來源本身不算重複；新增情境、證據、反例、用法、讀者問題或時間更新可以構成再寫的理由。反過來，若候選素材已被既有內容實質吸收，且沒有新增問題、證據或用途，優先合併、縮為短訊、連回既有內容或暫不成篇，不因素材可延伸就再開一篇。比較資料只涵蓋已登記範圍時，明示範圍與缺口，不宣稱已排除所有重複；不能為了補齊歷史而無限擴大檢索。

若用 Decision Node 協助分類，輸入須綁定實際比較資料版本，並保存各原子問題、最後處置與來源定位。缺少直接上文、候選正文或既有內容時，使用可路由的 `needs_context` 回來源或真人，不用更強模型重讀同一個缺口；只有比較資料齊全但語意仍無法可靠分類時才 `abstain` 並升級。一般模型產生的機率只用來觀察分布與決定是否升級，不能當成已校準的正確率；來源、候選或既有內容改變後，舊決定失效。

<a id="source-selection"></a>

## 2. 找少量候選

本節用於尚未選定題目的工作。固定期間編選先完成該期間的來源盤點，再挑入選單元；指定題目則直接處理，不額外製造候選供作者挑選。

來源依作者或工作區設定決定，可能包含貼文、回覆、工作紀錄、逐字稿、讀者問題、研究、客服、案例或舊電子報。先讀容易取得、前後關係清楚、已整理的近期資料；只有找不到好題目或需要補證據時，才回查大型原始紀錄。

候選優先考慮：

- 有具體事件、問題、選擇、結果、問題語言或值得整理的外部內容。
- 有足夠來源，不需要 AI 補造作者內容。
- 符合刊物的閱讀期待；原始紀錄需要編排，但作者近況或多話題週報本身不是不合格類型。
- 有可辨認的閱讀價值；深入文章聚焦問題，編選可讓讀者跟上一段期間的多個話題。
- 與這份電子報目前的作用，或正在誠實驗證的問題有關。

若使用者要估算可單獨延伸的庫存，先將同一問題的主文、回覆、重發與跨期補充去重，再列「現有來源可直接寫」「補少量可取得的證據後可寫」「需要作者新輸入」及無法判讀的來源缺口。每個數量要能回到獨立題目與來源定位，並標明盤點日期與範圍。不能用貼文數、互動量或目標字數換算篇數，也不能把缺上文的回覆當成一個已成立題目。這只是庫存判斷，不自動生成所有草稿。

<a id="writing-basis"></a>

## 3. 寫清楚本期必須做到什麼

以下問題只供內部寫作與檢查使用：

- 發生了什麼，或這次選了什麼材料？
- 真正值得讀者花時間的是什麼？
- 哪些是事實、作者內容、外部來源、AI 推論與未知？
- 讀者打開前，處在什麼看得見、說得清楚的情況？
- 作者為什麼適合談這件事？根據是什麼？
- 讀者看完後能理解、辨認、決定、嘗試、回應或行動什麼？
- 有哪些時效、隱私、授權、歸屬、承諾與不可公開範圍？
- 哪一種內容類型最適合，而不是 AI 最熟悉哪一種？
- 這條內容路線要完成什麼特有價值：深文如何改變判斷、編選如何讓多個單元可讀，或短札記／通知／策展如何完成自身任務？

這份內部答案稱為「本期寫作依據」。它不是正文固定段落，也不需要原樣交給讀者。

只記對本次決策有用的資訊，不把所有問題變成必填欄位。共用部分包括路線、讀者、來源定位、公開範圍與重要限制；深入文章補主要問題和必要深度，編選補期間、理解單元與重要取捨。原始資料由原處維護，不為寫作依據再建全量副本。

判斷型或案例型深文的寫作依據，還要先形成一條可被來源支持的判斷推進：讀者可能從哪個既有理解出發、這篇改問哪個更準確的問題、哪些證據會改變判斷、同一判斷能遷移到哪裡及何時不能套用。具體判準與 AI 邊界見[研究依據與內容類型](content-model.md#判斷型深文的推進主線)。AI 先從來源提出少量候選、標示依據與未知，再選出本篇能真正回答的一條；不能用「多數人都以為」補造讀者心理，也不能把作者未表達的立場當成反轉。週報編選、通知與短札記依自身任務成立，不必補成這條深文主線。

`brief` 完成後不直接寫全文。先用選題 JEV 判斷內容處置，再用 `brief` Gate 檢查已選定的任務契約。`revise` 時 AI 只修改 issue contract 後重跑；`recover_sources` 回查來源；`author_only` 才停給作者。這一關最多回修兩次，連續兩輪沒有改善就停止，不再增加其他審查者硬湊通過。

來源上的專案名、路徑、識別與私人註記可能只供回查，不能因它們出現在素材裡就搬進正文。寫作依據分清可用事實、僅供追溯的內容及公開限制；正文需要證據時保留讀者可理解的事實或必要來源，不要求讀者解碼內部紀錄。

本期寫作依據要保存所有會影響正確性與責任的內容；正文只選擇完成本期讀者任務所需的部分。這兩層不能互相取代：沒有寫進正文，不代表資料可以遺失；資料很重要，也不代表讀者必須在這一封信裡全部讀完。依文章類型選擇必要的具體情況、關鍵線索、取捨、機制、證據、結果、限制或適用方式，其餘留在內部供查核與後續選題。

## 4. 安排理解路徑

以下是需要展開解釋時的參考功能，編選則依單元與實際內容關係組織：

```text
讓讀者進入具體情境或問題
→ 及早知道本期為什麼值得讀
→ 依文章類型，提供足夠的事件、選擇、方法、材料或關係
→ 讓讀者看見限制、可以怎麼使用，或接下來能做什麼
→ 說完這封信要幫讀者完成的事就停下
```

完整成稿與整期審稿使用 [讀者關係與作者原意](reader-and-author-fidelity.md) 的閱讀門檻方法，處理開頭、必要背景、推理與中斷後承接；減少額外負擔時仍保住來源與必要深度。這些是編輯判斷，不增加固定摘要、導讀卡或文末作業。

長內容同時安排可略讀的入口：主旨與開頭交代問題，資訊性小標或段落入口標示正在回答的子問題，重要轉折接回主線，結尾完成本篇承諾。這不是固定版型；短文不必為此硬加小標。

故事、方法、研究、作者近況、邀請回信的問題與下一步行動，都只在內容需要時加入。安排順序應跟著素材和讀者接下來自然會問的問題，不要照研究項目或固定模板排列。

### 把編修註直接放在對應文字旁

需要把稿件交給作者、編輯或其他 AI 修改時，正文成形後，將編修註直接插在主旨、預覽文字或承重區塊之前。不要另外做一張要求接手者來回對照的地圖。這些註解不是預先規定文章外觀的模板，而是對本篇現有文字的就地說明。

專案沒有指定語法時，使用容易搜尋及整批移除的標記，分清兩種用途：

```text
〔編輯註｜供參考：這裡保留適用條件，改寫時別把局部經驗寫成普遍結論。〕
〔編輯註｜需確認：兩份紀錄的採用方案不同，請確認當天用的是甲還是乙。〕
```

「供參考」不需要作者回覆；「需確認」才是待辦，必須對應無法從來源處理、會改變內容的問題。沒有必要就不加。只標示真正承重的區塊，不必逐句解說；以下是可說明的內容，按需選擇，不必逐項填滿：

- 讀者到這裡需要跨過哪個理解缺口。
- 這一塊對本期讀者任務及電子報穩定價值的貢獻。
- 為什麼出現在這裡，以及它如何承接前後內容。
- 修改時必須保留的事實、推理關係、作者立場、限制或公開邊界。
- 哪些只是當前句子、例子、長度或順序，可以自由調整。

編修註保護的是內容功能與推理關係，不是 AI 寫出的原句。若一段無法說明自己增加了什麼，優先合併、刪除或重寫；人工改動論證結構時，也就地更新相鄰註解。工作稿可保留註解，乾淨寄送版則移除完整的 `〔編輯註｜…〕` 標記及其中內容。註解若與正文同一行，不可刪掉整行正文；同時排除內部資料區與 metadata，再確認必要背景、證據、限制沒有只留在註解裡。

### 人類改稿後，AI 依註解復核

行內編修註是人與 AI 共用的結構契約，不是 AI 對自己文章的解說。作者可以改寫所有句子、搬動段落、合併或刪除內容；下一輪 AI 不以字面相似度判斷好壞，也不得因文字不同就恢復舊稿。

AI 復核時逐則檢查註解所保護的功能，使用以下結果：

- **已保留：**功能、根據與邊界仍在原處成立，文字可以完全不同。
- **已移位承接：**原處已改或刪除，但其他位置完整接住同一功能；指出承接位置，不要求搬回。
- **被弱化：**仍有提到，但不足以完成原本的讀者理解、證據或限制工作。
- **已遺失：**全文已找不到這項必要功能，而且作者沒有明示要放棄。
- **作者已改變目標：**只有作者明確改變主張、讀者任務或取捨時使用；同步更新註解與受影響的前後結構，不用舊契約否決新方向。

AI 接回作者的直接改字、留言或口述，自行檢查主旨、預覽、相鄰段落、證據與限制是否仍一致。對有來源且方向明確的「被弱化」「已遺失」或新增衝突，完成最小修正；無法判定作者是否刻意改變意思時，才指出具體缺口確認。不要只交一份修正建議要求作者執行，也不為了維持註解而恢復舊方向。

交回同一份整合稿，簡短說明實質改動與仍待決處。局部修改可指出需複閱的段落；若主張或全篇結構改變，明說需要重讀。乾淨閱讀版可以在核准前產生，但不因此移除內部待決狀態；最終發布版移除內部資訊後仍須檢查連續性及確切版本。

<a id="draft-completeness"></a>

## 5. 先完成可反應雛形

形成雛形時，檢查正文是否完成本次約定的閱讀任務，而非把內部報告或資料堆疊換成口語句子。深入判斷或案例文章應讓讀者看見起點理解為何需要修正、真正問題、改變判斷的證據與適用邊界；這些功能可以自然分布在正文，不必露出四個欄位名稱。編選可有多個話題，各單元補足上下文並形成可讀編排；通知、策展或社群內容依自身用途成立。不因缺少故事、單一主張或教學結論便否定稿件。

完成來源能支持的：

1. 建議主旨；必要時附少量替代版本。主旨不能承諾正文沒有提供的內容。
2. 預覽文字；只有平台需要，或它能補充主旨時才提供。
3. 完整正文或足以讓作者反應的雛形。
4. 來源註記、AI 推論與哪些資訊可以公開，留作內部確認。

不要因為等待作者，就把 AI 能完成的結構與確認工作留白；也不要把一串問題當成草稿。

**以下深度檢查適用於承諾分析、案例、教學或解釋的內容。** 純編選使用 compilation-method 的完成條件；其中某個單元若本來就承諾解釋，仍須說到足以理解，但不能為通過深度檢查而新增作者理由。

把「段落都有安排」和「內容已經完整」分開檢查。使用者要的是完整判斷、案例、教學或策展信時，不要因為已經有開頭、主張與結尾，就把實際上只有事件摘要加結論的短札記標為完整。進入文字後製前，先依 [研究依據與內容類型](content-model.md) 的完成條件確認：讀者是否看得到足以評估或轉用主張的具體情況、關鍵線索、取捨或機制、證據或目前結果、限制，以及適用方式。每期不必全部都有，但來源明明能支持更多必要內容時，應先補齊，再處理文字精簡。內容選擇的目標是去掉與本期任務競爭的支線，不是把文章變短；若重建後只剩摘要、口號或結論，應補回必要深度，而不是把「信件感」判為已改善。

「提到」一項內容，不等於已經把它說到足以使用。對本期真正承重的內容，逐項確認讀者能否回答：具體發生了什麼或要做什麼、為什麼形成這個判斷、在什麼條件下成立、哪裡可能失敗，以及自己可以怎麼評估或採用。不是每項都要回答全部問題，但如果一個重要機制、證據或限制只用一句話帶過，讀者仍無法評估，這項深度就還沒有完成。

來源很豐富時，在內部比較一次「來源能支持的重要內容」和「正文實際使用的內容」。被排除的材料應該是競爭支線、過度細節、不能公開或留待後續，而不是因為稿件已經有開頭和結尾就被省略。這個比較是深度檢查，不是要求把所有來源塞進正文。

若來源只夠支持短札記，就誠實縮小這期任務；若缺的是會改變文章的作者經驗或判斷，就進入「等待作者回答」。不要用固定字數硬撐，也不要讓「每段都有作用」被誤做成「愈快收束愈好」。

## 6. 取得作者回答並整理進文章

依 [reader-and-author-fidelity.md](reader-and-author-fidelity.md) 執行：

- 來源完整且沒有值得請作者補充的本篇觀點時，可零提問直接進入品質 Gate；全部通過後才是「可以審稿」（`review_ready`）。
- 先回查來源，再判斷能否保留未完成、縮小或移除非必要內容；不能用刪掉核心問題來冒充完成。仍缺會實質改變文章的作者回答時，交付可反應內容與確切問題，狀態設為「等待作者回答」（`author_input_pending`）。題數由缺口決定，一題就只問一題。
- 編選缺少原文未說的理由、經驗或結論，不自動追加訪談；依編選任務保留邊界。深入文章則只補完成本篇問題必要的作者內容。
- 作者可用聊天、批註或口述回答；不要求先寫成文章。
- 整理時保留原意、立場、語氣力道與不確定，再重新檢查全文結構與事實。

完整寫作後先判斷是否仍缺作者輸入：沒有值得問的問題便直接進來源與主張 Gate；有問題時，先保存具主旨與正文邊界的可反應稿，留下單一具體問題、為何要問、以及答案會影響稿件哪裡。給作者看的 `question` 必須是第一次看到也能直接回答的完整問句；備課脈絡、編輯理由、答後安排各放在說明欄，不把一整段內部註記冒充成一道題。作者回答整合回同一工作稿，再進受影響的品質 Gate。只有連不預設作者答案的安全雛形都不能寫時，來源、brief 或初稿階段才提前停下，並記錄不能先寫的原因與已試過的縮小主張、保留未知或調整任務方式。作者回答不是 Gate PASS，也不是作者接受；必要決定沒有答案不能進品質 Gate；深入文章若有具體取捨或觀察能補出本人判斷，可邀請作者回答或略過。後者不是補洞，不問泛泛感受、語氣偏好，也不要求作者代寫。

<a id="editorial-review"></a>

## 7. 審查、回修與交稿

完整初稿完成後，依 [Gate 與回修迴圈](#quality-loop)逐段驗證，不把所有品質要求塞進一次「整體看起來如何」的評分。順序固定為：

1. **來源與主張：**查事實、因果、第一人稱、引句、時間及公開權限。
2. **完整與深度：**查本篇承諾是否完成，必要背景、推理、案例與限制是否足以讓讀者評估。
3. **閱讀體驗：**查啟動、背景、推理、中斷、略讀路徑、未讀與日後使用負擔，也查是否用操控語言或多重 CTA 奪走讀者選擇；降低門檻不能刪掉前一關已確認的必要理解。
4. **作者與公開：**查語氣力道、立場、作者修改、敏感範圍及與近期文章的重複。
5. **文字與聲音後製：**前四關都通過後，依固定方法檢查公開文字；有具體問題才定點修改，改稿後從第一個受影響的 Gate 重新複驗。
6. **確切版本交作者：**在作者審閱前執行，查最新版、前置 Gate、匯出範圍、主旨、預覽、連結與正文一致；通過不等於作者已接受。

每一關都核對確切版本、寫作依據與所需直接來源，不能以其他面向的好表現抵銷一個成立的實質問題。原寫作者自查不能冒充正式 Gate；JEV 直接讀 Gate input，不接收 AI 預先寫好的自評或預期結論。JEV 不可用時便保留未驗證狀態，不增加假紀錄。

每項問題留下短原句、來源定位、造成的誤解與最小修訂範圍。分清違反事實／作者意思或妨礙讀者任務的實質問題，以及可選的語氣偏好。引句應可逐字回查；省略或合併須明示，不能拿改寫句冒充原句。

審查也是待核對的判斷。看完整上下文再決定：必要意思是否只是移位？條件推論是否被誤當實測？案例當時的技術狀態是否被誤當本輪編輯指令？未解釋的術語可能造成閱讀障礙，但不是看到英文或內部名稱就一律判違規。公開識別則回到明示的使用範圍，不能以「某某專案」自動當成匿名。

Prose Gate 只管套版痕跡、重複、節奏及場域語氣；前面 Gate 負責事實、深度、讀者理解與作者意思，不讓它取代內容審查。AI 依[文字與聲音後製](prose-and-voice.md)及專案提供的 `voice_reference` 診斷，再把確切候選交 JEV `prose` 判斷；不把通用「自然」取代作者本人。缺少必要資料或 JEV 執行失敗時不能留下通過 Receipt，也不能進入作者審閱；恢復後重跑。

<a id="bounded-revision"></a>

### 只修成立的問題，再看修法有沒有傷到內容

保存修改基準後，回修角色接回成立的問題或作者改動，處理受影響文字與必要相鄰承接；沒有實質問題就保留原稿。來源不足回來源，核心主張不成立回本期寫作依據，不能把所有問題都變成潤飾或全文重寫。若作者回饋或 Gate 已證明問題橫跨全文──例如第一人稱主線被摘要掉、各段均勻得像報告、內容容量遠低於來源──可在完整來源、原稿與保護清單都保留時採一次結構重建；先列缺陷與不可遺失內容，再另產候選，不用局部縫補冒充修復。任何正文回修都從來源與主張 Gate 重新複驗；這是檢查改法有沒有帶入新傷害，不是要求每次重寫全文。

改完同時核對兩件事：原問題是否消失；這個改法有沒有新增事實、作者慣例、過強因果，或讓原意、深度、條件與自然度受損。正在被檢查的稿句不能替自己的爭議主張作證；逐項回到直接來源、作者回答或已核對紀錄，來源只支持其中一項就只保留該項。對齊作者原話仍可能造成繞口的回補；不能只看問題清單已勾完。來源已支持的必要承接要保留，真的只是重複才刪除。

複驗回到受影響的 JEV Gate，範圍由實際差異決定。新增主張或結構改變需要連讀全篇；單句修訂只查原句、相鄰推理與受影響主張。相同問題反覆出現時先診斷來源、任務或修法，不盲目要求「再最佳化一次」。每一張 receipt 都只證明該 Gate 對該輸入版本的結果，不把實驗用的多輪完整盲審設成日常配額。

<a id="author-handoff"></a>

### 交給作者的是完整稿，交接的是確切版本

正文、主旨與必要預覽是閱讀主體；來源、寫作依據、待決、審查及狀態留在同一工作稿的內部區。必要編修註就地標「供參考」或「需確認」，不再抄成整份問卷。只交付當前需要的版本與說明，不要求作者從多份候選自行拼稿。

會改變數字、名稱、案例、作者立場、公開範圍或承諾的核心缺口仍留在正文時，內容是 `author_input_pending`。只有真的完成不含待決資訊的安全版本，才能讓那個版本進入 `review_ready`；不是把必要問題改稱不阻擋。作者回答、事實與使用範圍齊備，完成應有檢查後才交可審稿件。初期仍需作者完整閱讀，不承諾只看幾個修改處就能負責。

作者在舊預覽修改時，對照匯出基準、作者修改與目前工作稿，以目前稿接回實際差異，保留最新更正。找不到基準或遇到意思衝突，只釐清受影響段落；整合後只維護一份正文。原稿快照供回查，不是另一份待維護稿。舊版核准及檢查不自動套用新版；重新核對受影響內容與當前版本，再更新狀態。

作者改字、留言或口述後，AI 自行處理能由來源決定的修改，檢查主旨、預覽、前後段及限制。分辨原意保留、移位、弱化、遺失與作者明確改變目標，不能因字面不同就恢復舊句。原意或公開範圍確實只有作者能決定時才問；回饋定位、查背景與一般邏輯修正不交回作者重做。

清除內部註解時不能連同同一行正文刪掉，必要公開證據與限制也不能只放在註解裡。乾淨閱讀版仍可保留內部待決狀態，只有真正接受當前版本才記 `approved`。交下游時附版本、用途與對象、未解限制、接手者及完成證據；內容交接不代表平台驗證、名單確認、排程或寄送。

## 8. 最後檢查

1. **這封信要完成的事：**本期閱讀期待是否清楚？深入文章是否聚焦問題，編選是否讓讀者理解所收錄的單元？多話題不等於失焦。
2. **電子報的作用：**內容是否符合這份電子報目前的作用，而不是固定寫成專家觀點、教學或強硬銷售？
3. **來源：**事實、作者內容、外部來源、推論與未知是否分清楚？
4. **文章類型：**文章的寫法是否由素材和讀者需要決定？
5. **稿件種類：**正文是否完成約定的內容任務，而非原始資料堆疊或內部報告換成口語？
6. **判斷推進：**若是判斷型或案例型深文，讀者是否看得出舊理解為何不夠、新問題如何成立、哪些證據真正改變判斷，以及能轉用到哪裡和何時不能套用？這不是所有電子報的固定格式。
7. **是否容易理解：**依讀者關係方法檢查第一次進入、中斷、略讀與漏期後的閱讀；略讀提示與細節深度符合本期任務，必要背景、推理與限制沒有因精簡而消失。
8. **每段的作用：**每一段是否增加事實、根據、關係、限制、選擇，或讀者能怎麼使用？
9. **人工能否接手與交回：**必要編修註是否就地說清功能與可改表達，並分清供參考和需確認？AI 是否尊重功能移位與作者新方向，完成可處理的修正？正文能否連續閱讀，是否只有一份可修改版本？
10. **忠於作者：**作者為什麼適合談這件事是否有根據？整理時是否保留原意？
11. **讀者關係：**是否具體、尊重自主，不使用假同理或壓力套路？若有下一步，是否自然且沒有把多個動作一起變成義務？
12. **可以公開嗎：**個資、客戶資訊、價格、承諾、版本、數字與內容歸屬是否正確？
13. **結尾與下一步：**該說的事情說完後是否停下？安排的下一步是否自然，而且連到正確的地方？

任何高風險事實、隱私或對外承諾尚未確認時，不能標為「可以審稿」（`review_ready`）以上。

一次生產多封，或準備連續出刊時，把可用稿件一起讀，檢查是否反覆使用不適合內容的固定骨架。編選的穩定欄目可能有助閱讀，不因重複外觀就重寫。也不等待另一條內容線完成，才准許本篇結束；各篇的來源、核准與狀態各自成立。

累積三至六封可比較的 `review_ready` 或實寄內容後，在下一輪選題前做一次系列回看，不增加每篇必跑 Gate。並讀這些確切版本，檢查讀者是否仍得到同一種穩定服務、不同內容路線是否各自成立、開頭／轉折／證據／結尾是否只剩同一骨架，以及 CTA 或延伸是否累積成負擔。結果只調整下一輪配置、brief 或刊物承諾，不回頭把已成立的不同題型修成同一外觀；未滿三封或沒有可比較版本時標為資料不足，不虛構趨勢。

同一刊物有多種內容時，以各篇自身的閱讀任務與成熟度安排交付，不預設其中一種是另一種的預告、附件或續篇。互相引用只在有具體幫助且目的地已可閱讀時加入，正文仍保留必要背景；明確要做系列則依使用者選擇設計。共用素材可重用，新增理解、事實更正與文字風格修改分開處理：更正查受影響文章，局部改寫不要求全系列同步。平台、全文交付與寄送時點由實際專案決定，編輯規劃不授權寄送。

交給發布或其他用途時，只補下游真正需要的確切版本、用途與對象、未解限制、接手者及完成證據。內容 `review_ready` 或 `approved` 不能當成平台測試或寄送成功；排程、名單、寄送與技術異常由負責系統處理。若本次只要求內容，交稿到此完成，不擅自擴張為發布任務。

## 9. 寄出後至少留下什麼

依可取得資料分開記錄：

- 製作成本：人類投入、等待、決策次數、重述要求與重大返工；需要時再分到來源、選材、審稿等階段，不要求作者填繁複日誌。
- 內容問題：錯誤、失焦、加工過度、公開不當，或前後銜接不自然。
