# Sepia 文字後製

本文件說明 `newsletter-production` 為什麼使用 Sepia、何時使用、選哪一種操作，以及文字變好讀後如何保住電子報必須說清楚的內容。

## 來源與證據邊界

- 官方程式庫：[Nanako0129/sepia](https://github.com/Nanako0129/sepia)
- 上游研究與來源：[Sepia research](https://github.com/Nanako0129/sepia/tree/main/research)
- 流程讀取目前工作環境可用的 Sepia 或等價文字後製方法；每次執行把載入方法的版本／內容 identity 留在 Work Snapshot 與 Receipt。電子報走 technical article／blog 路線，並把專案提供的 `voice_reference` 視為明示疊加的作者聲音依據。若方法不可用，仍可依本文件做人工化診斷，但不得宣稱執行過未載入的外部 Skill。
- 任一作者或語言上的效果都必須用當地案例驗證；不得把其他作者的測試結果當成通用證明。

Sepia 提供 `write`、`review`、`refactor`、`recreate` 四種操作。電子報預設先使用 `review`；局部問題用 `refactor`。若完整來源與原稿均已保留，而且缺陷清單證明問題是全篇結構性的──例如作者主體被摘要掉、所有段落被壓成同一節奏、短稿已無法靠局部手術補回來源容量──才使用 `recreate` 另產候選，並重新通過全部內容 Gate。它沒有權限決定內容真相、作者立場、公開範圍或最終核准。

既有長篇測試中，Sepia 減少了過度工整的小節、重複總結與集中句型，但也曾把正文縮短約 33%，使一段重要角色分工變薄。後續三題型測試中，兩篇有實質問題而重整，一篇因原結構承擔必要案例因果而只 review、不改寫。這支持「先看段落功能，再決定是否修改」，不支持按詞頻、工整度或縮短比例自動重寫。

## 分工

- `newsletter-production` 決定本期讀者任務、必要內容、來源、作者回答、可公開範圍與稿件狀態。
- Sepia 在完整草稿完成後診斷文字問題，必要時做最小幅度重整。
- `newsletter-production` 比較原稿與 Sepia 候選，只補回被改壞或遺失的重要內容，刪除沒有來源的新內容，再檢查主旨、預覽文字與正文是否一致。

## 使用條件

先確認稿件完成自身的閱讀任務：深入文章已展開必要解釋，編選的各單元可讀且忠實，其他類型依約定用途成立。若仍只是內部報告或原始材料堆疊，先回到本期寫作依據處理；不能只因編選有多個話題、未完成觀察或固定欄目，就要求重建成單一論說文。

作者回答、主要事實與公開範圍已確認，且四道內容 Gate 通過後，才對讀者實際看到的主旨、必要預覽文字與正文執行 Sepia `review`。本期寫作依據、私人素材與完整來源只供內部核對，除非診斷確實需要，不交給外部工具。

只有 `review` 找到下列實質問題時才進入修改；局部問題執行 `refactor`，跨全文的主線或結構問題才考慮 `recreate`：

- 小標、段落或強調位置的工整安排實際妨礙理解；穩定欄目與作者原有節奏本身不是問題。
- 同一結論反覆換句話說。
- 問題、因果或教學內容只沿單一路線排列，像套模板。
- 同一種轉折、句型或節奏集中出現。
- 文字語氣不符合電子報與讀者的實際關係，或把來源已有的作者主體全面改寫成中性報告。

先保存問題清單，依 [審查方法](production-method.md#editorial-review)核對原句、來源與讀者後果；`refactor` 只處理成立的問題及必要相鄰承接。`recreate` 先抽出事實、主張、作者原話功能、限制與不可遺失內容，再從空白重建；不能拿舊稿摘要當唯一來源。案例裡的技術狀態不自動等於編輯指令外漏，偏好也不能冒充實質缺陷。沒有實質問題就保留原稿，不為展示工具而改寫。`write` 不取代素材整理與作者訪談；`recreate` 仍需使用者對本次結構重建的明示授權，不能由一般自動後製自行擴張。

## 改寫後的內容核對

1. 從本期寫作依據列出不可遺失的事實、作者判斷、形成過程、讀者用途、限制、反例、公開邊界與主旨承諾。
2. 保留固定原稿；Sepia 輸出另存候選稿，不得覆蓋原稿。
3. 逐項標示重要內容是完整保留、移位、壓縮但完整、改壞、遺失，或新增無來源內容。
4. 只用原始來源或作者回答補回被改壞、遺失的最小必要內容；刪除無來源的新內容。
5. 依 [讀者關係與作者原意](reader-and-author-fidelity.md) 核對理解入口與承接。必要背景、概念澄清及中斷後接回，不因沒有新增事實或用了連接詞就刪掉；確認它是否真的幫讀者理解，再判斷重複。若新版只剩摘要，依路線回查必要內容：深入文章的機制、證據與限制，編選的具體情境、原有說法與未完成。不可為補深而新造作者意思；字數變短本身不是成功證據。
6. 補回後只做銜接與最後檢查，不再次自動重整全文。
7. 來源對齊後再讀修改句，確認沒有為塞回原話而變得繞口；只交付整理完成的單一候選版本；它仍是 `review_ready`，不能因通過 Sepia 自動變成 `approved`。

## 處理狀態怎麼記

- `not_applicable`：本次是規劃、局部修改、尚待關鍵作者輸入，或只測編輯決策，沒有進入完整文字後製。不要因此新增一個補跑待辦。
- `sepia_not_run`：本次確實需要完整後製，但必要文件取得失敗、執行中斷或依本次限制未執行；說明原因，不宣稱檢查完成。
- `reviewed_no_refactor`：已依實際文件完成 review，沒有需要改寫的問題。
- `refactored_and_reconciled`：已完成必要改寫，並核對與接回原意、深度及閱讀承接。

未執行與不適用是不同判斷；只完成文字編輯示例的測試，不證明 Sepia 程序有執行。

## 可用性與版本

- 當次有可讀的 Sepia Skill 時，完整讀取其 `SKILL.md` 及該操作要求的 references，記錄實際版本與規則。Sepia 是可由 AI 依文件執行的編輯程序；沒有 CLI 不等於不能執行。
- 未安裝 Sepia 但允許讀取公開網路時，可從官方程式庫取得當前規格；記錄實際版本或 commit，不能把「讀過官方程式庫」說成「已安裝」。
- 必要文件無法取得時標記 `sepia_not_run`，說明缺少什麼。自動完整製作停在本 Gate，不產生 Sepia 通過 Receipt，也不進作者審閱；其他不依賴 Sepia 的局部工作仍可進行。不得憑記憶模擬或聲稱已通過。
- 升版時用同一固定原稿比較文字改善與內容保留；新版本通過前，不沿用舊版測試結論。

Sepia 是有來源、可查版本的優先後製方法，不是內容 authority，也不能跳過負責人核准。完成 review 與必要的局部 refactor 後，直接以該確切版本進入 `sepia` Gate；若仍有成立問題，由主 AI 依 receipt 定點修復，不再交給另一個全文潤稿模型重寫。
